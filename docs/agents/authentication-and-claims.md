# Authentication, Proxy, roles, and custom claims

## Proxy contract

`src/proxy.ts` and `src/lib/supabase/supacharger/proxy.ts` are shared core behaviour distributed by the CLI. Create one request-scoped Supabase server client and perform exactly one `getClaims()` identity check. Exclude `is_anonymous` identities unless `ALLOW_ANONYMOUS_USERS` is true. Proxy must not call database RPCs or perform profile, onboarding, billing, organisation, or product lookups.

Use `src/supacharger/auth/server-access.ts` from protected server layouts and handlers for `requireVerifiedUser()`, `readAppAccessState()`, and `requireAppAccess()`. These checks are authoritative at the server boundary but do not replace handler-specific authorisation, grants, or RLS.

Whenever `@supabase/ssr` changes auth cookies, preserve the mutated request cookies, response cookies, and its `Cache-Control`, `Expires`, and `Pragma` headers on every continuation, redirect, rewrite, and error response. Use `src/supacharger/auth/proxy-response.ts` and its `copySupabaseResponseState`; do not create a replacement response that drops this state.

Route configuration is `PATH_AUTH_GUARD` (the former `PATH_AUTH_GARD` spelling is not supported). Use `src/supacharger/auth/route-policy.ts` for exact paths, `:param` segments, and trailing `:param*` wildcards. Paths declared in `UNAUTHED_USER.ALLOWED` are public marketing or authentication surfaces. Protected API paths return JSON `401` responses; page paths may redirect with a safe relative `next` destination. Product-specific public routes remain developer configuration or adapters outside the session adapter.

Keep Next.js crawler metadata endpoints outside Proxy matching. `/robots.txt` and `/sitemap.xml` must return their direct text/XML responses without session refresh, localisation, authentication, onboarding, rewrite, or redirect handling, just like the platform association documents under `/.well-known/`.

## Configured authentication journey

`AUTHENTICATION` is the canonical feature policy. `EMAIL_PASSWORD.SIGN_IN` and `SIGN_UP` gate password operations. `PASSWORDLESS_EMAIL.SIGN_IN` and `SIGN_UP` independently select one exclusive mode: `disabled`, `otp`, or `link`; they never request both credentials in one passwordless email. A sign-in request always sets `shouldCreateUser: false`, while a configured passwordless signup may create the user. `PASSWORDLESS_EMAIL.OTP_LENGTH` is an integer from 6 through 10 and controls every rendered OTP field. `SIGN_UP_EMAIL_VERIFICATION` remains a separate password-signup policy and accepts `disabled`, `otp`, `link`, or `otp-and-link`. `MFA_TOTP.ENABLED` advertises whether the application supplies a second-factor journey. UI and server actions must enforce these values.

`NEXT_PUBLIC_SITE_URL` is the single runtime source for the canonical application origin. Read it through `getSiteUrl()` and construct paths with `getURL(path)`; never add a localhost or production fallback in application code. Missing configuration must fail clearly. Supabase's hosted URL allow-list remains separately configured, while a local `config.toml` may reference the same environment variable.

Successful OAuth PKCE callbacks must redirect through `USER_REDIRECTS.AUTHED_USER.LOGIN_REDIRECT_DESTINATION`, not directly to the Site URL. Passwordless email uses the separate token-hash `/auth/confirm` flow. `AUTHED_USER.HOME_PATH` remains the general authenticated home and may differ from the post-login destination when `/` is a public marketing page. Append the protected one-time login notice through `getAuthLoginRedirect()` so `AuthLoginNotice` shows the localised `AuthTerms.loginSuccess` toast and removes the query parameter. Billing access is an independent product policy: `BILLING_ACCESS.REQUIRED` may divert a callback before the normal login destination, while applications that do not force subscription access must leave it disabled.

The shared clean-room journey uses SnapScreen as its approved visual and interaction basis. Preserve the strong heading treatment, progressive provider-to-email transition, dark auth surfaces, branded primary actions, and matching password-reset presentation across Core, SnapScreen, and Wakekeeper. Keep auth buttons and input fields at the shared 56 px height with 20 px by 12 px internal padding. OTP entry renders exactly `PASSWORDLESS_EMAIL.OTP_LENGTH` fields and uses the same length for Zod validation, messaging, and verification. Preserve distinct sign-in wording and `VerificationPurpose`: passwordless codes verify with `type: 'email'`, while password-signup confirmation codes verify with `type: 'signup'`. Preserve a safe relative `next` destination through route switches, sends, resends, and successful verification; reject absolute and protocol-relative destinations. Keep password, link, and OTP pending indicators action-specific. Client-facing Auth Server Actions return only selected plain success data or a safe `{ code, status }` error. Keep branding, copy overrides, product fields, and post-authentication actions in developer-owned adapters. Extend shared states within this presentation; do not replace it with a generic form or add application edits inside CLI-managed form files. Specdrive retains its separate Untitled UI presentation.

Password signup must use the protected Server Action so the authoritative Zod parse, enabled-method policy, and safe error projection run on the server before `auth.signUp()`. Retain the submitted email and change local presentation state only after the action succeeds. Continue to use `startTransition` for imported Auth Server Actions initiated by login, signup, magic-link, and OTP controls.

Use `src/components/ui/loading-spinner.tsx` as the canonical indeterminate loader. It renders the developer-owned `src/assets/svgr/ui/inline-loader.svg` through SVGR, so replace that single asset to change inline loading globally; callers must not import the SVG directly or add a second animation. Give standalone loaders a localised `label`, while decorative button loaders remain hidden from assistive technology. OTP verification cross-fades this loader into a green circle with a white Lucide tick before redirecting.

`AUTH_PROVDERS_ENABLED` is a complete boolean map for the canonical social OAuth provider union: `apple`, `azure`, `bitbucket`, `discord`, `facebook`, `figma`, `github`, `gitlab`, `google`, `kakao`, `keycloak`, `linkedin_oidc`, `notion`, `twitch`, `x`, `twitter`, `slack_oidc`, `slack`, `spotify`, `workos`, and `zoom`. Render only enabled providers and reject disabled values in the server action as well as hiding them in the UI. Prefer `linkedin_oidc`, `slack_oidc`, and `x` for new integrations; the unqualified Slack and Twitter keys exist for legacy Supabase providers. Provider artwork is managed under `src/supacharger/assets/svgr/auth-providers/`. Email, Phone, SAML, and Web3 artwork may be present there but does not make those method-specific flows ordinary OAuth providers.

Passwordless email uses Supabase's hosted **Magic Link or OTP** template, and its contents must match the selected exclusive mode. OTP mode contains `{{ .Token }}` and no login link; link mode contains the token-hash link and no OTP. `signInWithOtp()` uses `shouldCreateUser: false` for sign-in and nominates the safe confirmation redirect. Entered passwordless codes call `verifyOtp({ email, token, type: 'email' })`. Password-signup verification is independent: `disabled` requires confirmations off, `otp` uses the configured-length token, `link` uses a token-hash link, and `otp-and-link` may include both alternatives in the **Confirm signup** template. Signup codes call `verifyOtp({ email, token, type: 'signup' })`; when both alternatives are sent, consuming either may invalidate the other. Keep `PASSWORDLESS_EMAIL.OTP_LENGTH`, local `[auth.email] otp_length`, and the hosted OTP-length setting equal. A copied local `config.toml` or template never configures the hosted project. `/auth/confirm` validates safe destinations and token hashes; `/auth/callback` remains reserved for OAuth code exchange. `EMAIL_RESEND_COOLDOWN_SECONDS` must not be shorter than the hosted Auth rate limit.

Mobile verification uses the developer-owned `MOBILE_DEEP_LINKING` identifiers and the protected generated association routes. OTP code entry does not require deep linking; magic-link, link-confirmation, and reset callbacks do. Preserve the PKCE verifier boundary by completing the callback in the same web view or native Supabase client that initiated it. Follow `docs/agents/mobile-auth-deep-linking.md` before changing the association documents, Proxy exclusions, callback bridge, or native setup guidance.

Proxy provides session refresh and optimistic page routing only. Route Handlers and Server Functions authenticate their own requests, domain services enforce application permissions, and RLS plus grants remain authoritative. Do not use `getSession().user`, `user_metadata`, Proxy redirects, or UI state as an authorisation decision.

## Canonical global role

`app.user_roles` is the private source for a user's global application role. `app.custom_access_token_hook(jsonb)` runs as `supabase_auth_admin` through the Auth Hook configuration and emits a top-level `user_role` claim. Only `supabase_auth_admin` may read the table through its narrow RLS policy or execute the hook; browser roles receive neither privilege.

Assign roles through reviewed migrations or a separately approved trusted administrative boundary. Never expose a self-assignment RPC. A role update does not change an already-issued JWT; require a session refresh and treat the database as authoritative when revocation must be immediate.

## Resource-scoped roles and organisation context

Do not force organisation, team, project, or account membership into `app.user_roles`. The canonical dormant foundation is `app.organisations`, `app.organisation_members`, and `app.user_session_contexts`. `ORGANISATIONS.ENABLED` controls exposure, not installation. Organisation creation or selection uses the service-only `api_edge` adapters after authentication; never place an organisation handle in arbitrary Auth metadata. A compact active-context claim may help navigation, but it is derived from server-owned session context, refreshed after switching, bounded in size, and checked against membership at the data boundary.

The hook emits `active_organisation_id`, `active_organisation_handle`, `active_organisation_role`, and `organisation_context_version` only when a valid session context exists. Product-specific organisation fields and onboarding presentation remain application-owned.

## CLI and deployment

Create role/hook changes with `supabase migration new`, verify a clean local reset and database lint, regenerate local types, and keep `[auth.hook.custom_access_token]` pointed at `pg-functions://postgres/app/custom_access_token_hook`. A hosted project also requires the hook selection under Authentication → Hooks; `config.toml` alone changes only the local stack.

The Supacharger CLI must preserve developer configuration, distribute the config contract and migrations, preview linked migration changes, and never silently mutate a hosted database. Keep migration and dashboard steps in release/upgrade guidance.
