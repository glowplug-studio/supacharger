# Authentication, Proxy, roles, and custom claims

## Logout session policy

`SUPABASE_AUTH.SESSION.SIGN_OUT_ALL_DEVICES` is a build-time application security policy. The canonical starter defaults to `true`: managed logout explicitly uses Supabase's `global` scope and revokes every Auth session for that user. Set it to `false` to use `local`, which revokes only the session used for logout and preserves independently signed-in browsers, phones and companion apps. `local` still revokes a server session; it does not mean clearing browser cookies alone. Already-issued access tokens can remain valid until expiry, so another affected device may discover global logout only on its next refresh.

Keep the property in every developer-owned configuration and deploy the application after changing its value. CLI updates add a missing key with `true` and preserve existing booleans; an older configuration missing the key also retains global logout at runtime during migration. Selecting `false` changes security behaviour and requires the relevant approval. The policy affects the managed `logoutUser` action only; protocol cleanup such as rejected session-transfer redemption remains explicitly local. No database migration or hosted Supabase session-policy change is required. See [Supabase's sign-out scopes](https://supabase.com/docs/guides/auth/signout).

## Authenticator assurance

Managed Supabase Auth TOTP enrolment and factor management are always available at `/account/security`; there is no application visibility flag. `SUPABASE_AUTH.METHODS.MFA_TOTP.REQUIRED_FOR_SIGN_IN` checks `getAuthenticatorAssuranceLevel()` after password and email-OTP sign-in and in the OAuth/PKCE callback. An enrolled AAL1 session is sent to the managed `/account/mfa` challenge with only an allowlisted relative `next` path. Challenge success raises the session to AAL2 before navigation resumes. Local projects must enable both `auth.mfa.totp.enroll_enabled` and `verify_enabled` in `supabase/config.toml` and restart the local stack. Hosted Auth capability remains a separate Dashboard setting.

Use Supabase Auth factors only: list, enrol, challenge/verify, and unenrol. Never create an application MFA table or persist the TOTP secret. Treat unverified factors as incomplete enrolments, allow cancellation, and require a fresh code for factor removal when the session must step up. `REQUIRED_FOR_SIGN_IN` cannot manufacture a factor; a user with no verified factor has no AAL2 challenge until enrolment.

## Cross-device session transfer

`SUPABASE_AUTH.METHODS.CROSS_DEVICE_SESSION_TRANSFER` is disabled by default. Its TTL must be an integer from 60 through 300 seconds; use 120 unless a product has an approved reason to shorten it. `POST /api/auth/session-transfers` remains protected and accepts only strict JSON with an optional safe relative `next`. `/auth/session-transfer` and `POST /api/auth/session-transfers/redeem` are public protocol routes so an unauthenticated receiving browser can redeem; both return `404` while disabled.

Issue requires a verified, non-anonymous user, a confirmed email, a live `session_id`, same-origin mutation headers and AAL2 when the configured MFA policy requires it for an enrolled account. Store only a SHA-256 digest of the 256-bit base64url grant. The URL carries the raw grant in its fragment; the minimal bootstrap clears it before a single credentialled POST and loads no analytics or third-party resources.

Claim is atomic and one-use. The trusted server fetches the known user, creates an unsent Supabase magic-link token, verifies it immediately through the request-scoped SSR client, checks the exact user ID, and never returns or persists the generated Auth token properties. This creates a distinct AAL1 receiving session. Route success through the existing callback adapter so MFA, onboarding, billing and the stored destination remain canonical. A receiving session for another user fails closed; the same user continues without minting another session. Never copy source access or rotating refresh tokens.

Email and password settings are separate from profile details. Their managed server routes authenticate with `getUser()`, validate payloads with Zod, and reauthenticate the current password before `updateUser`. OAuth-only accounts must show password-dependent controls as unavailable.

## Proxy contract

`src/lib/supabase/client.ts`, `src/lib/supabase/server.ts`, `src/proxy.ts`, and `src/lib/supabase/supacharger/proxy.ts` are shared core behaviour distributed by the CLI. Keep `cookies.encode: 'tokens-only'` consistent across clients accessing browser, server-request, and Proxy cookies. During server rendering of Client Components, the browser factory omits browser-only options and uses the SDK's cookie-free fallback; authenticated server operations must use the request-scoped server factory. This stores the browser-side user object separately while keeping only token state in shared cookies, preventing a refresh from expanding request headers with a duplicate Auth user record. Server code must use `getClaims()` for verified claims or `getUser()` for a fresh Auth record; `getSession()` is only for raw token state and its `user` field must not be used. Create one request-scoped Supabase server client and perform exactly one `getClaims()` identity check in Proxy. Exclude `is_anonymous` identities unless `ALLOW_ANONYMOUS_USERS` is true. The managed Proxy and session adapter must not perform profile, onboarding, billing or organisation lookups. The developer-owned project request guard may perform a narrowly scoped availability lookup after authentication routing, using the existing verified client; see Project request guard below.

Use `src/supacharger/auth/server-access.ts` from protected server layouts and handlers. `requireVerifiedUser()` performs no profile or billing RPC, `requireOnboardedUser()` applies the configured profile-completion policy without a billing RPC, and `requireAppAccess()` applies onboarding first and then configured billing access. `readAppAccessState()` exposes the same ordered state for server consumers. These checks are authoritative navigation boundaries but do not replace handler-specific authorisation, grants, or RLS.

Recovery destinations must sit outside the guard they recover: profile setup belongs under a verified-only layout, billing acquisition under an onboarded layout, and full product routes under `requireAppAccess()`. Use route groups to preserve public URLs. Do not add pathname exceptions to the generic access helpers.

Whenever `@supabase/ssr` changes auth cookies, preserve the mutated request cookies, response cookies, and its `Cache-Control`, `Expires`, and `Pragma` headers on every continuation, redirect, rewrite, and error response. Use `src/supacharger/auth/proxy-response.ts` and its `copySupabaseResponseState`; do not create a replacement response that drops this state.

Before creating the request-scoped Auth client, remove known password, email, MFA, and organisation-registration fields from query strings on `/account`, `/auth` and `/organisation` routes. Preserve unrelated safe return parameters, capture a valid `lang` handoff in the locale cookie, and redirect to the sanitised URL. Keep the field list and path detection in `src/supacharger/auth/sensitive-auth-query.ts`; forms must still use POST and authoritative server-side validation because query sanitisation is defence in depth, not a submission boundary.

Keep the shared option shape, supported modes, managed route and form implementation, semantic presentation interface, and required English keys portable across consumers without prescribing a developer-owned application's selected passwordless mode, confirmation setting, sidecar contents, CSS values, root-layout composition, or formatting style.

Route configuration is `PATH_AUTH_GUARD` (the former `PATH_AUTH_GARD` spelling is not supported). Use `src/supacharger/auth/route-policy.ts` for exact paths, `:param` segments, and trailing `:param*` wildcards. Paths declared in `UNAUTHED_USER.ALLOWED` are public marketing or authentication surfaces. Protected API paths return JSON `401` responses; page paths may redirect with a safe relative `next` destination. The bare root destination `/` is implicit and must not be appended as `?next=%2F`; root destinations with a query string or fragment remain explicit. Product-specific public routes remain developer configuration or adapters outside the session adapter.

Keep the complete Next.js `/_next/` framework namespace outside Proxy matching so development assets and HMR never enter authentication routing. Keep crawler and application metadata outside it as well: `/robots.txt`, `/sitemap.xml`, platform association documents under `/.well-known/`, and `.webmanifest` files must return their direct responses without session refresh, localisation, authentication, onboarding, rewrite, or redirect handling. Permit only the narrow `127.0.0.1` hostname through `allowedDevOrigins` when loopback-origin development requests need to reach a server started on `localhost`.

## Configured authentication journey

The public user-facing routes `/account/login`, `/account/create`, `/account/login-magic`, and `/account/reset-password` live under `src/app/(supacharger)/(unauthenticated)/` and are exact managed Core. `/auth/callback`, `/auth/confirm`, and `/auth/error` are managed protocol/error routes. `/account/reset-password/new` shares the unauthenticated presentation shell but requires a verified, non-anonymous Supabase user; it is not a public entry point. Do not add duplicate public paths under another route group because Next.js cannot resolve two pages to the same URL. The route shell and forms expose stable `sc-auth-*` hooks, import `AuthSidecar` and `AuthMobileBrand` from the developer-owned adapter, and receive presentation from `src/styles/supacharger-auth.css`. The CLI installs the adapter and stylesheet only when absent and preserves them on later updates.

`AUTHENTICATION` is the canonical feature policy. `EMAIL_PASSWORD.SIGN_IN` and `SIGN_UP` gate password operations. `PASSWORDLESS_EMAIL.SIGN_IN` and `SIGN_UP` independently select one exclusive mode: `disabled`, `otp`, or `link`; they never request both credentials in one passwordless email. A sign-in request always sets `shouldCreateUser: false`, while a configured passwordless signup may create the user. `PASSWORDLESS_EMAIL.OTP_LENGTH` is an integer from 6 through 10 and controls every rendered OTP field. `SIGN_UP_EMAIL_VERIFICATION` remains a separate password-signup policy and accepts `disabled`, `otp`, `link`, or `otp-and-link`. The managed TOTP factor journey is always exposed; `MFA_TOTP.REQUIRED_FOR_SIGN_IN` alone controls AAL2 enforcement for enrolled accounts. UI and server actions must enforce this value.

`NEXT_PUBLIC_SITE_URL` defines the canonical origin for metadata and background links through `getSiteUrl()` / `getURL()`. Auth and billing destinations use the validated request-origin helpers described below. Supabase redirect configuration remains separate.

Successful OAuth PKCE callbacks must redirect through `USER_REDIRECTS.AUTHED_USER.LOGIN_REDIRECT_DESTINATION`, not directly to the Site URL. Passwordless email uses the separate token-hash `/auth/confirm` flow. `AUTHED_USER.HOME_PATH` remains the general authenticated home and may differ from the post-login destination when `/` is a public marketing page. Append the protected one-time login notice through `getAuthLoginRedirect()` so `AuthLoginNotice` shows the localised `AuthTerms.loginSuccess` toast and removes the query parameter. Billing access is an independent product policy: `BILLING_ACCESS.REQUIRED` may divert a callback before the normal login destination, while applications that do not force subscription access must leave it disabled.

Treat `USER_REDIRECTS.UNAUTHED_USER.LOGOUT_REDIRECT_DESTINATON` as a safe application-relative path. `POST /account/logout` clears the request-scoped SSR session and returns `{ success: true, redirectTo }`; the managed button navigates to that relative path and must not use `response.url`. `GET /account/logout` supports developer-owned direct-navigation controls and responds with `303` plus a relative `Location` header, which the browser resolves against the incoming request origin. Do not construct logout navigation from `NEXT_PUBLIC_SITE_URL`: a stale host, scheme, or port must not turn a successful cookie clear into a client-visible failure.

The shared clean-room journey uses SnapScreen as its approved visual and interaction basis. Preserve the strong heading treatment, progressive provider-to-email transition, dark auth surfaces, branded primary actions, and matching password-reset presentation across Core and Wakekeeper. SnapScreen is the historical reference and is excluded from synchronisation unless explicitly requested. Keep auth buttons and input fields at the shared 56 px height with 20 px by 12 px internal padding. Anchor the password-requirements checklist absolutely below the relative password-strength wrapper; it must float above following content without changing form height or covering its own password input. Keep signed-in password and confirmation fields in separate rows at every viewport width. OTP entry renders exactly `PASSWORDLESS_EMAIL.OTP_LENGTH` fields and uses the same length for Zod validation, messaging, and verification. Preserve distinct sign-in wording and `VerificationPurpose`: passwordless codes verify with `type: 'email'`, while password-signup confirmation codes verify with `type: 'signup'`. Preserve a safe relative `next` destination through route switches, sends, resends, and successful verification; reject absolute and protocol-relative destinations. Keep password, link, and OTP pending indicators action-specific. Client-facing Auth Server Actions return only selected plain success data or a safe `{ code, status }` error. Keep branding, copy overrides, product fields, and post-authentication actions in developer-owned adapters. Extend shared states within this presentation; do not replace it with a generic form or add application edits inside CLI-managed form files. Specdrive retains its authorised presentation by implementing the same adapter and semantic CSS seams; its former user-facing `/auth/*` pages redirect for one documented release and retain only an allowlisted safe `next` value.

Password signup must use the protected Server Action so the authoritative Zod parse, enabled-method policy, and safe error projection run on the server before `auth.signUp()`. Retain the submitted email and change local presentation state only after the action succeeds. Continue to use `startTransition` for imported Auth Server Actions initiated by login, signup, magic-link, and OTP controls.

Password changes post to the protected `/api/account/update-password` Route Handler. It strictly parses the current/new password payload with Zod, verifies the current Auth user, reauthenticates through `signInWithPassword`, applies the configured strength policy, then calls `updateUser`. Do not add a password-comparison RPC or database password oracle.

Password recovery follows Supabase’s SSR token-hash flow. The email template sends `TokenHash` with `type=recovery` to `/auth/confirm`; the Route Handler calls `verifyOtp` and redirects to `/account/reset-password/new` after successful verification. The new-password page and protected `/api/account/recover-password` boundary require a verified, non-anonymous user through `getUser`. The endpoint strictly parses both password fields with Zod, applies the configured password-strength policy used by signup, and calls `updateUser`; Supabase enforces its password-update policy. Both password endpoints map Supabase `same_password` to HTTP 400 with `{ "error": "samePassword" }`; both forms render `SupabaseErrorCodes.samePassword` in the toast and inline message. Unexpected update failures remain generic. Do not require a particular AMR value. Never skip token verification because an unrelated session exists: invalid recovery links must still fail.

Use `src/components/ui/loading-spinner.tsx` as the canonical indeterminate loader. It renders the developer-owned `src/assets/svgr/ui/inline-loader.svg` through SVGR, so replace that single asset to change inline loading globally; direct SVGR use of the same primary asset is permitted, but do not add a competing inline animation. Follow [loading guidance](loading-ui.md) for accessibility and ownership. Give standalone loaders a localised `label`, while decorative button loaders remain hidden from assistive technology. OTP verification cross-fades this loader into a green circle with a white Lucide tick before redirecting.

`SUPABASE_AUTH.OAUTH_PROVIDERS` is a complete boolean map for the canonical social OAuth provider union: `apple`, `azure`, `bitbucket`, `discord`, `facebook`, `figma`, `github`, `gitlab`, `google`, `kakao`, `keycloak`, `linkedin_oidc`, `notion`, `twitch`, `x`, `twitter`, `slack_oidc`, `slack`, `spotify`, `workos`, and `zoom`. Render only enabled providers and reject disabled values in the server action as well as hiding them in the UI. Prefer `linkedin_oidc`, `slack_oidc`, and `x` for new integrations; the unqualified Slack and Twitter keys exist for legacy Supabase providers. Provider artwork is managed under `src/supacharger/assets/svgr/auth-providers/`. Email, Phone, SAML, and Web3 artwork may be present there but does not make those method-specific flows ordinary OAuth providers.

Passwordless email uses Supabase's hosted **Magic Link or OTP** template, and its contents must match the selected exclusive mode. OTP mode contains `{{ .Token }}` and no login link; link mode contains the token-hash link and no OTP. `signInWithOtp()` uses `shouldCreateUser: false` for sign-in and nominates the safe confirmation redirect. Entered passwordless codes call `verifyOtp({ email, token, type: 'email' })`. Password-signup verification is independent: `disabled` requires confirmations off, `otp` uses the configured-length token, `link` uses a token-hash link, and `otp-and-link` may include both alternatives in the **Confirm signup** template. Signup codes call `verifyOtp({ email, token, type: 'signup' })`; when both alternatives are sent, consuming either may invalidate the other. Keep `PASSWORDLESS_EMAIL.OTP_LENGTH`, local `[auth.email] otp_length`, and the hosted OTP-length setting equal. `/auth/confirm` validates safe destinations and token hashes; `/auth/callback` exchanges OAuth PKCE codes and accepts legacy recovery callbacks during deployment; new recovery emails use `/auth/confirm`. `SUPABASE_AUTH.EMAIL.RESEND_COOLDOWN_SECONDS` must not be shorter than the hosted Auth rate limit.

Mobile verification uses the developer-owned `MOBILE_DEEP_LINKING` identifiers and the protected generated association routes. OTP code entry does not require deep linking; magic-link, link-confirmation, and reset callbacks do. Preserve the PKCE verifier boundary by completing the callback in the same web view or native Supabase client that initiated it. Follow `docs/agents/mobile-auth-deep-linking.md` before changing the association documents, Proxy exclusions, callback bridge, or native setup guidance.

Proxy provides session refresh and optimistic page routing only. Route Handlers and Server Functions authenticate their own requests, domain services enforce application permissions, and RLS plus grants remain authoritative. Do not use `getSession().user`, `user_metadata`, Proxy redirects, or UI state as an authorisation decision.

## Canonical global role

`app.user_roles` is the private source for a user's global application role. `app.custom_access_token_hook(jsonb)` runs as `supabase_auth_admin` through the Auth Hook configuration and emits a top-level `user_role` claim. Only `supabase_auth_admin` may read the table through its narrow RLS policy or execute the hook; browser roles receive neither privilege.

Assign roles through reviewed migrations or a separately approved trusted administrative boundary. Never expose a self-assignment RPC. A role update does not change an already-issued JWT; require a session refresh and treat the database as authoritative when revocation must be immediate.

Core calls `app.custom_access_token_claims_extension(event jsonb, canonical_claims jsonb)` after producing the canonical role and active-organisation claims. The default extension returns an empty object. Applications may replace only this function through a new forward migration and return compact product-owned claims. The managed hook rejects Supabase-required, optional, global-role, and active-organisation claim names so product code cannot override the Core trust contract.

Keep the extension `security invoker`, grant execute only to `supabase_auth_admin`, and give that role only the table grants and RLS policy required by the product query. Never edit an applied migration, put personal data or unbounded collections into a JWT, or use `user_metadata` as an authorisation source.

## Resource-scoped roles and organisation context

Do not force organisation, team, project, or account membership into `app.user_roles`. The canonical optional foundation is `app.organisations`, `app.organisation_members`, invitations, access requests, and `app.user_session_contexts`. `ORGANISATIONS.ENABLED` controls exposure, not installation. Every organisation action calls the authenticated `api.organisations(input_payload)` dispatcher, which derives identity, verified email, and session state from the JWT; never accept client-supplied user/session identifiers or place an organisation handle in arbitrary Auth metadata. A compact active-context claim may help navigation, but it is derived from server-owned session context, refreshed after switching or other context-changing mutations, bounded in size, and checked against current membership at the data boundary.

The hook emits `active_organisation_id`, `active_organisation_handle`, `active_organisation_role`, and `organisation_context_version` only when a valid session context exists. Removing a member or changing a role invalidates stale contexts, and callers must refresh the session when the RPC returns `requiresSessionRefresh`. Product-specific organisation fields and presentation remain application-owned.

## CLI and deployment

Create role/hook changes with `supabase migration new`, verify a clean local reset and database lint, regenerate local types, and keep `[auth.hook.custom_access_token]` pointed at `pg-functions://postgres/app/custom_access_token_hook`. `config.toml` changes only the local stack.

For every hosted environment, complete and verify this separate release operation:

1. Confirm the canonical migration is present in the hosted migration ledger.
2. Use an organisation or project Owner or Administrator account; Developer and Read-Only roles cannot update Auth configuration and may receive `403` from the dashboard or Management API.
3. Open **Authentication → Hooks**, choose **Custom Access Token**, select the **Postgres Function** or **SQL** type, and select exactly `app.custom_access_token_hook`.
4. Enable and save the setting. Do not create a duplicate function or select a similarly named function in another schema.
5. Obtain a newly issued token by signing in again or refreshing the session, then verify with `supabase.auth.getClaims()` that `claims.user_role` exists.

Treat a successful password login without `user_role` as a failed hosted-hook verification. If the database ledger and local configuration are current, inspect the hosted selection and account permissions rather than adding compatibility code or changing the application to trust user-editable metadata.

The Supacharger CLI must preserve developer configuration, distribute the config contract and migrations, preview linked migration changes, and never silently mutate a hosted database. Keep migration and dashboard steps in release/upgrade guidance.

## Refresh contention and outage containment

Session renewal follows [Supabase’s Next.js SSR guide](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs). Each request creates its own server client; React cache only shares it within a render request. Proxy calls `getClaims()` immediately after creating its client. The SDK refreshes expired sessions, and `setAll` passes updated cookies to both the incoming request and outgoing response, including Supabase’s cache-prevention headers. Redirects and project guards preserve that response state.

Supabase owns token storage, rotation, refresh retries and session clearing. Core does not intercept the token endpoint, retain token responses in a process-wide cache, impose custom refresh admission limits or decode session cookies itself. `isLoggedIn()` uses the SDK’s verified `getClaims()` result. Keep browser, server and Proxy clients on the same supported `tokens-only` encoding; never trust `getSession().user` for authorisation.

Core classifies retryable Auth transport failures, HTTP 408/429/5xx, timeouts and recognised database or network availability errors centrally. During Proxy verification, these failures return a private, no-store HTTP 503 with `Retry-After: 30`: browser requests receive a standalone connection page, while API requests and Server Actions receive `auth_temporarily_unavailable`. Protected account page guards and the organisation-context handler also distinguish transient service failures from invalid authentication; account pages enter recovery rather than redirecting to login, and organisation-context failures return HTTP 503 with the same retry guidance. Core does not clear a session merely because a dependency is unavailable. Permanent invalid-session errors retain normal authentication routing; direct Supabase endpoints retain their own status codes and hosted rate limits.

The SDK’s initial refresh retries and cookie behaviour remain unchanged. Once the standalone recovery page opens, it starts a separate ten-second reconnect window with short retry intervals. If recovery has not succeeded after ten seconds, the page displays “We’re having issues” and continues checking at thirty-second intervals. This window does not impose a ten-second limit on the SDK’s earlier refresh attempt. Recovery uses the read-only `/auth/availability` probe to check identity and, for a verified user, database availability; it never replays the failed mutation. Successful recovery returns to the safe relative destination, while a confirmed unauthenticated response resumes ordinary authentication routing. The recovery document and probe remain reachable during authentication outages. The Core widget gallery embeds `/auth/unavailable?demo=1`, which uses the real standalone warning without making recovery probes. Both outage and 404 previews remain visible until the gallery is reloaded. Only the demo response permits same-origin framing; real outage responses cannot be framed.

## Password recovery email contract

Follow [Supabase’s password recovery guide](https://supabase.com/docs/guides/auth/passwords?flow=pkce). `sendPasswordReset` validates the email on the server and calls `resetPasswordForEmail(email, { redirectTo })` with the validated request-origin confirmation URL. The hosted recovery template contains:

```html
<a href="{{ .RedirectTo }}?token_hash={{ .TokenHash }}&amp;type=recovery">Reset password</a>
```

Set Supabase’s Site URL to the application’s canonical HTTPS origin. `/auth/confirm` validates the token/type, calls `verifyOtp` with `type=recovery` and redirects to `/account/reset-password/new`. The password-write endpoint independently validates the payload and verifies the current user with `getUser` before `updateUser`. Supabase enforces its password-update policy. Token-hash verification issues an `otp` AMR; Core does not require a custom recovery AMR or add a separate recovery credential. Recovery ignores arbitrary `next` destinations. Invalid, expired or consumed recovery tokens redirect to `/auth/error?flow=recovery`, even if the browser already has another session. Tokens and raw Auth errors are excluded from redirects.

OAuth still uses the PKCE `/auth/callback`. Existing recovery PKCE links remain accepted there during deployment, but new recovery templates use token hashes and do not require the initiating browser’s verifier. Deploy Core and consumers, then install their hosted templates. The hosted allow-list must accept each request-origin confirmation destination. `NEXT_PUBLIC_SITE_URL` remains the canonical URL for metadata and background links.

## Project request guard

`src/supacharger.adapters/request-guard.ts` is a developer-owned, default-no-op adapter. Export `resolveProjectRequest` using `ProjectRequestGuard` from `src/supacharger/request-guard-contract.ts`. Return a NextResponse to stop rendering, or null to continue. It runs after session verification and authentication redirects, and receives the same verified request client; do not construct another Auth client or verify the session again. Use narrowly matched, bounded availability checks where a real status code must be decided before streamed rendering. Authorisation remains in route handlers and database policies. Thrown errors return a blank, private 503 response; do not convert transport failures to missing resources. All replacement responses preserve the latest session cookies and auth cache headers. Default consumers make no additional database calls.

The CLI installs this starter only when missing and preserves custom adapters on upgrades. Canonical Proxy, session adapter and contract must be synchronised together. No configuration property or database migration is added. The session adapter exposes its existing client plus getResponse() solely to retain current cookie state across the guard.

## Canonical URL and request domains

`NEXT_PUBLIC_SITE_URL` remains the required canonical origin for metadata, sitemap and links generated without a request. `getSiteUrl()` and `getURL()` are for those canonical links. They do not select the domain for authentication or Stripe returns.

Server Actions use `getRequestOrigin()` / `getRequestURL()`; Route Handlers use `getAppRequestOrigin(request)` and `appURL(path, origin)`. These validate the incoming origin and build only safe application-relative paths. OAuth, signup/resend, passwordless links, recovery, email changes, Stripe Checkout/Portal and session-transfer journeys retain the initiating domain. Internal navigation should use relative paths.

The canonical origin is allowed automatically. Exact `VERCEL_URL` and `VERCEL_PROJECT_PRODUCTION_URL` deployment origins are also allowed when present. For additional custom domains, set server-only `APP_ALLOWED_ORIGINS` to a comma-separated list of complete origins, for example `https://alias.example.com,https://other.example.com`. Omit it for a single canonical domain. No wildcard hosts are accepted. Request Origin and Host/forwarded-host must agree; unknown origins are rejected, never silently redirected to the canonical domain. A reverse proxy must preserve the public request URL and supply consistent host/protocol headers.

Register the same supported domains and actual redirect destinations in Supabase Auth's redirect allow-list. Recovery sends `redirectTo=<origin>/auth/confirm`; signup and email changes also supply a complete `/auth/confirm?next=...` URL. Recovery templates append `?token_hash=...&type=recovery` to the query-free `RedirectTo`. Signup and email-change templates append `&token_hash=...&type=...` to their query-bearing `RedirectTo`. Never append another route. Query-bearing redirect destinations must match the hosted allow-list; do not register token-bearing links. Keep Supabase Site URL as the default for dashboard/admin/background operations without an explicit destination. Invitations issued without an application request keep that default.

Deploy application changes before installing the new hosted recovery template. Local templates do not update hosted Auth. Cookies remain domain-scoped: preserving a domain does not create cross-domain SSO. Native associations must also be configured on each supported native-link host. No database migration is needed for request-domain routing.

## Recovery feedback and email-change confirmations

After a reset request succeeds, the form keeps an inbox confirmation visible and offers resend after `SUPABASE_AUTH.EMAIL.RESEND_COOLDOWN_SECONDS`. Resend uses the same password-recovery endpoint, not signup verification. Root-level legacy token-hash links are forwarded to `/auth/confirm` before the page guard; verification remains mandatory.

Email changes support both native `ConfirmationURL` templates and token-hash `type=email_change` templates. Native links return to `/auth/confirm?next=/account/security`; a PKCE code is exchanged through `/auth/callback`. With secure email change enabled, the first accepted link displays a prompt to check the other inbox. Only completed verification displays completion; failed tokens remain failures even in an authenticated browser. The fixed Supabase pending message is informational and never authorises access.

The hosted Site URL must use the production HTTPS origin. Allow-list the exact `/auth/confirm` and `/auth/callback` destinations and their query-bearing forms on every supported origin. A rejected redirect silently falls back to Site URL. Username is nullable in storage so administrative creation and invitations can create the mandatory profile before onboarding; apply the forward reconciliation migration on older installations retaining a NOT NULL constraint.

Logout at `/account/logout` bypasses Proxy session refresh, page guards and product guards so a missing or expired session cannot redirect its POST to login. The handler owns SDK sign-out and cookie clearing. POST returns JSON; GET returns a 303 with a safe relative Location. All outcomes use `Cache-Control: private, no-store`. Other protected routes retain their guards.
